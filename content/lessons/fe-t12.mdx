As apps grow, prop drilling hurts and server-cache state needs tools. The professional rule: **server state** (TanStack Query), **global client state** (Context or Zustand), **local state** (useState).

## Context: built-in, but watch the re-renders

```jsx
const ThemeCtx = createContext(null);

function App() {
  // ❌ new object every render → every consumer re-renders
  // <ThemeCtx.Provider value={{ theme, setTheme }}>

  // ✅ memoized value object
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeCtx.Provider value={value}>{children}</ThemeCtx.Provider>;
}

function Button() {
  const { theme } = useContext(ThemeCtx);
  return <button className={theme}>Click</button>;
}
```

Context is a broadcast to every consumer. Fine for low-frequency values (theme, auth user) — painful for fast-changing ones (keystrokes, hover).

## Zustand: stores without ceremony

```jsx
import { create } from "zustand";

const useCart = create((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
}));

// component — selector limits re-renders to what you read
const count = useCart((s) => s.items.length);
const add = useCart((s) => s.add);
```

No provider, no boilerplate, selectors keep re-renders surgical.

## The decision table

| State | Home |
|---|---|
| Server data (jobs, profile) | Query cache (TanStack Query) |
| Auth user, theme | Context |
| Cart, UI preferences | Zustand store |
| Form inputs, toggles | useState in the component |

3. Write a one-paragraph "state inventory" of your app: what lives where and why.
