ORMs give type-safe, composable queries — but only pay off if you understand the SQL they generate. Schema design is where juniors can contribute real value early.

## The schema IS the design

```prisma
model Job {
  id        String   @id @default(cuid())
  title     String
  company   Company  @relation(fields: [companyId], references: [id])
  companyId String
  skills    JobSkill[]
  createdAt DateTime @default(now())

  @@index([companyId])
}

model JobSkill {
  job      Job    @relation(fields: [jobId], references: [id])
  jobId    String
  skillId  String
  minScore Int
  @@id([jobId, skillId])  // composite PK = no duplicates
}
```

Many-to-many with extra data (minScore) needs an explicit join model. Constraints in the schema beat "we check in code" every time.

## Queries: avoiding N+1

```js
// ❌ N+1: one query for jobs, then ONE PER JOB for skills
const jobs = await prisma.job.findMany();
for (const j of jobs) {
  j.skills = await prisma.jobSkill.findMany({ where: { jobId: j.id } });
}

// ✅ one query, joined in
const jobs = await prisma.job.findMany({ include: { skills: true } });
```

N+1 is the #1 ORM performance bug — recognize it in code review.

## Migration discipline

```bash
npx prisma migrate dev --name add-job-skills
```

Small, named, reviewable migrations. Adding a column? Make it nullable, backfill, then constrain — never break the running version.

## Practice — do these, don't just read

1. Model the blog schema from Stage-2 (users, posts, comments, tags) in Prisma; run migrations.
2. Write a query that would be N+1, then fix it with `include` — feel the difference.
3. Add a column without downtime: nullable first, backfill script, then constrain.
