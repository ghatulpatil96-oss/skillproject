Speed and scale come from not doing work twice. Caching and queues are the two tools every backend engineer reaches for when the database becomes the bottleneck.

## Cache-aside in four lines

```js
async function getJob(id) {
  const cached = await redis.get(`job:${id}`);
  if (cached) return JSON.parse(cached);        // hit

  const job = await db.job.find(id);            // miss → DB
  await redis.set(`job:${id}`, JSON.stringify(job), "EX", 300); // 5-min TTL
  return job;
}
```

App checks cache → DB on miss → populate. TTL bounds staleness; **invalidation on write** is the hard part (`redis.del("job:42")` after update).

## What to cache (and not)

Good: read-heavy, rarely-changing, expensive-to-compute — job listings, product pages, computed leaderboards.
Bad: user-specific data without a user-scoped key, anything written-then-read-immediately, auth checks.

## Rate limiting: the counter pattern

```js
const key = `rl:${ip}:${Math.floor(Date.now() / 60000)}`; // per-minute window
const hits = await redis.incr(key);
if (hits === 1) await redis.expire(key, 60);
if (hits > 100) return res.status(429).json({ error: "Slow down" });
```

## Queues: slow work leaves the request

Sending email takes 800ms — inside a request handler that's a slow API for everyone:

```js
// handler: enqueue and respond immediately (202 Accepted)
await emailQueue.add("welcome", { userId: user.id });

// separate worker process: does the slow work, retries on failure
new Worker("welcome", async (job) => sendWelcomeEmail(job.data.userId));
```

Retries with backoff, idempotent jobs (safe to run twice), and monitoring the queue depth — that's production.
