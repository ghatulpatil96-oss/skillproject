Every API you build rides on the web's core protocol. Understanding HTTP, DNS, and REST semantics separates developers who configure frameworks from engineers who debug them.

## One request, end to end

You type `api.example.com/users`. DNS resolves the name to an IP, TCP opens a connection, TLS encrypts it, HTTP sends a request:

```http
GET /users?id=42 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGc...
```

…and reads the response's status line first: `200 OK`, `404 Not Found`, `500 Internal Server Error`. The status code is the API's headline; the body is the story.

## REST: resources and honest verbs

URLs are **nouns** (things), methods are the verbs:

```
GET    /jobs        # list
POST   /jobs        # create → 201
GET    /jobs/42     # read
PATCH  /jobs/42     # partial update → 200
DELETE /jobs/42     # remove → 204
```

An API that answers errors with `200 {success: false}` is lying to every client, cache, and monitor in its path.

## The headers that matter daily

`Content-Type` (what I'm sending), `Accept` (what I'll take), `Authorization` (who I am), `Cache-Control` (how long this is true), and the CORS trio when a browser from another origin comes knocking.

## Practice — do these, don't just read

1. Use curl against a public API: set headers, read status codes, follow redirects (`curl -i -L`).
2. Read SkillBridge's own `app/api/applications/route.ts` and map every response to a status code.
3. Design the resource layout (URIs + methods + statuses) for a library system: books, members, loans.
