System design interviews test judgment at scale. Nobody expects a junior to design Google — they expect clear reasoning about load, storage, and failure.

## The scaling ladder

1. **One box** — app + DB on a single server. Fine to thousands of users.
2. **Stateless app tier** — sessions move to Redis/signed cookies, so any server can serve any request.
3. **Load balancer** — distributes traffic across app servers, health-checks, removes dead ones.
4. **DB scaling** — read replicas for read-heavy loads, indexes and caching before sharding.
5. **Caching layers** — Redis in front of hot reads (the biggest cheap win).

## Back-of-envelope math (the senior move)

```
10,000 req/day = 0.12 QPS average, ~1 QPS peak → one small server
1,000,000 req/day = ~12 QPS average, ~120 peak → still one beefy box + cache
10M req/day = ~120 QPS avg, ~1,200 peak → app tier behind an LB
```

Numbers first. "How much traffic?" is the question that impresses.

## Worked example: URL shortener

- **API**: `POST /urls {longUrl}` → `201 {short}`; `GET /:code` → 301 redirect
- **Storage**: `code VARCHAR(8) PK, long_url TEXT, created_at` — ~1B rows × ~100B ≈ 100GB — one Postgres, indexed PK
- **Hot path**: redirect = 1 indexed read → cache top codes in Redis
- **Codes**: base62 of a counter (short, unique) vs random 8 chars (unguessable)
- **Failure mode**: DB down → cached redirects still work (reads dominate)
