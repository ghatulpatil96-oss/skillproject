Git is version control: the non-negotiable tool of every software team. GitHub is where that work becomes visible to recruiters — your commit history is part of your portfolio.

## The daily loop you'll repeat forever

```bash
git status                # what changed?
git add -p                # stage, reviewing hunk by hunk
git commit -m "Fix cart total when coupon exceeds subtotal"
git push origin my-branch # publish the branch
```

Commit messages should explain **why**, not what — the diff already shows what changed.

## Branches: parallel universes for code

```bash
git switch -c feature/search    # create + switch
# ...work, commit...
git switch main
git merge feature/search        # or open a PR instead
```

Merge conflicts are normal. When Git marks a conflict, edit the file to keep the right lines, remove the `<<<<<<<` markers, `git add` the file, and commit. That's the whole ceremony.

## The golden .gitignore

```gitignore
node_modules/
.env
dist/
```

Never commit dependencies (lockfiles yes, `node_modules` no) or secrets — anything in history stays in history forever.

## Practice — do these, don't just read

1. Put your roadmap projects on GitHub — one repo per project, clean history, real messages.
2. Create a branch, make changes, open a PR into your own main, review it, merge it.
3. Deliberately create a merge conflict with a friend (or two clones) and resolve it calmly.

## Common mistakes interviewers spot

- Commit messages like "update" or "fix stuff"
- One giant commit at the end of a week of work
- Committed API keys (they stay in history forever)
