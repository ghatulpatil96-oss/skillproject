Real apps are many pages sharing one shell. Routing, URL state, and data-fetching patterns define an app's architecture — and its UX quality.

## Routes, layouts, and the 404

```jsx
<BrowserRouter>
  <Routes>
    <Route element={<Layout />}>          {/* shared shell: nav + <Outlet/> */}
      <Route index element={<JobsList />} />
      <Route path="jobs/:id" element={<JobDetail />} />
      <Route path="*" element={<NotFound />} />
    </Route>
  </Routes>
</BrowserRouter>
```

Dynamic segments (`:id`) become params: `const { id } = useParams()`.

## URL as state

Filters that live in the URL survive refresh, are shareable, and make the back button work:

```jsx
const [params, setParams] = useSearchParams();
const q = params.get("q") ?? "";

<input value={q} onChange={e => {
  const next = new URLSearchParams(params);
  e.target.value ? next.set("q", e.target.value) : next.delete("q");
  setParams(next, { replace: true });
}} />
```

## Data fetching: who owns loading?

The core patterns:

- **Fetch-on-render**: component mounts → fetch → loading/error/data state per component. Simple; can waterfall.
- **Fetch-then-render** (route loaders / TanStack Query): data starts loading when navigation starts; the page arrives with data.
- **Render-as-you-fetch**: most advanced; rarely hand-rolled anymore.

If you reach for a library, TanStack Query is the industry default — it also caches (server state is not your local state).
