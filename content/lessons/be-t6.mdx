SQL is the most durable skill on this roadmap — databases outlive frameworks. Joins, indexes, and transactions separate a demo from a system that survives real users.

## Joins: thinking in sets

```sql
-- every job with its company name
SELECT j.title, c.name AS company
FROM jobs j
INNER JOIN companies c ON c.id = j.company_id;

-- LEFT JOIN keeps unmatched left rows (jobs with NO applications):
SELECT j.title, COUNT(a.id) AS applicants
FROM jobs j
LEFT JOIN applications a ON a.job_id = j.id
GROUP BY j.id;
```

The interview favorite: "INNER vs LEFT?" — LEFT preserves left rows that have no match (NULLs on the right); INNER drops them.

## Indexes: the trade

```sql
CREATE INDEX idx_applications_job ON applications (job_id);
```

Lookups on `job_id` go from full-scan to O(log n). Cost: slightly slower writes and extra storage. Index the columns you filter/join/sort on — not everything.

## Transactions: all or nothing

```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;  -- or ROLLBACK on any failure
```

Money moves, inventory decrements, seat bookings — anywhere partial completion is corruption.

## WHERE vs HAVING

```sql
SELECT company_id, COUNT(*) AS openings
FROM jobs
WHERE status = 'active'          -- filters ROWS before grouping
GROUP BY company_id
HAVING COUNT(*) >= 3;            -- filters GROUPS after aggregation
```
